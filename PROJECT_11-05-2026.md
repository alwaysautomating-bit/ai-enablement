# Project

Name: AI Enablement Workspace
Started: 07-24-2026
Status: Deployed preview — protected Vercel production deployment is runnable

## Purpose

A tiered AI workspace product that expands in capability as an organization's AI adoption
matures. Built for orgs with a healthy, non-paranoid AI posture that want systems — not
individual employee discipline — to carry the guardrail burden.

One-liner: the workspace expands with adoption, the guardrails scale with the workspace —
never with the person. Full design source: [FRAMEWORK_L0_L1_L2.md](./FRAMEWORK_L0_L1_L2.md).

## Problem

Most AI enablement today is either locked down (kills experimentation) or wide open (relies
on individual employees to self-police, which doesn't scale and doesn't hold up under
scrutiny). Neither approach lets an org's AI usage grow in step with demonstrated trust.
This project treats guardrails as an architectural property of the workspace tier, not a
policy document employees are expected to remember.

## Features

Canonical build inventory:
[FEATURE_CATALOG.md](./docs/FEATURE_CATALOG.md). The catalog assigns stable feature IDs, tier
boundaries, release phases, dependencies, and epic-level acceptance criteria. The list below
is the concise product summary.

- **L0 — Guided Deliverable Mode**: role-curated framework menu, persistent context,
  read-only connectors, guided input checklist, preloaded skill chain, and deliverable
  template. Nothing new gets created here — only used.
- **L1 — Connected Workspace Mode**: explicit per-connector write/action access and manual
  chaining of two or three approved frameworks. Governance becomes visible but remains fixed.
- **L2 — Builder Mode**: automations, agent-scaffolded small tools ("tiny SaaS, not
  platforms"), admin-gated governance edits. This is the dividing line — below L2 nothing
  new gets created, only used.
- **Review Gate**: mandatory, explicit-approval loop at every tier — Generate → Elevate →
  Review → Adjust → Approve. Scope scales from deliverable and source review at L0, to
  intended write/action review at L1, to reach and unattended-impact review at L2. Makes the
  human's defensibility work structural, not optional.
- **Privacy Scrubber (internal: Ephemeral Identity Vault)**: shared platform service across
  all workspaces. Reversible tokenization — detect sensitive values → token → isolated
  encrypted vault → AI only sees tokens → restore only recognized tokens against a canonical
  map (never literal find-and-replace) → re-scan output → hard-delete the vault mapping.
  Three handling modes: Standard masking, Strict de-identification, Restricted environment.
  Positioned explicitly as a best-practice privacy aid, not a HIPAA/GLBA/GDPR/CMMC compliance
  guarantee. Flagship use case: HR/manager workflows, where sensitivity currently makes people
  avoid AI entirely.
- **Promote Path**: private build → nomination (self or other) → light promotion review →
  attribution choice (named / anonymous / org tool) → promoted/shared state → attached
  support thread. Lets one person's L2 work raise everyone else's L0/L1 menu without
  requiring tier-climbing.
- **Open Door**: anyone, any tier, can observe how an L2 build works — no prerequisite.
  Cultural counterpart to Promote Path; moves understanding downward the way Promote Path
  moves outputs downward.
- **Stewardship model**: technical health (does it still run) is engineering's job; practice
  health (is this still the right approach) belongs to a domain/product owner. Collapsible to
  one person for small, well-built "tiny SaaS" builds — the two-role split is the fallback for
  builds that outgrow one person, not the default.
- **Vocabulary-Earned Communication**: first-time interfaces elicit the job in the user's
  language before introducing system terms. Precise vocabulary appears after successful use
  or on demand, never as a prerequisite for progress. Job description and technical
  configuration remain separate stages.
- **Context Capture (built on synthetic data; live Gmail/Slack next)**: bounded, read-only
  investigation over email and chat that reconstructs conversations, proposes candidate
  operational context with verified quotes, and turns human-reviewed items into dated
  relationships. When something was said and when it was true are kept separate.
  Permissions travel with every derived item. Codex and Claude read reviewed context and
  start captures through an MCP server and two portable skills.
- **Runnable L0 Research Assistant**: operational workspace shell, role-curated jobs,
  guided research direction, MVP forcing function, source selection, mock read-only shared
  drive, draft preparation, human attention flags, blocked approval, approval record, and
  responsive mobile behavior.

## Architecture

Frontend: Next.js 16 App Router, React 19, TypeScript, Tailwind CSS 4, custom responsive CSS
Backend: Next.js route handlers with Zod request validation and a governed run service
Database: Prisma 7 with local SQLite, checked-in SQL migrations, durable runs, revisions,
  sources, review items, approvals, memberships, and append-only audit events
AI: Server-side deterministic two-pass Research Assistant pipeline. Context Capture uses a
  provider-agnostic extraction interface (OpenAI and Anthropic implementations, structured
  output, deterministic quote verification) and a recorded test double for offline tests
Integration: local stdio MCP server (`scripts/mcp-server.mts`) with personal client tokens;
  portable `SKILL.md` skills in `skills/`
Infrastructure: Privacy Scrubber vault is planned as genuinely separate encrypted
  infrastructure from day one (own Supabase project or fully separate schema/credentials),
  not schema-level isolation as a stopgap — "practice as you mean to go on"
Deployment: Vercel project `ai-enablement`, connected to GitHub `alwaysautomating-bit/ai-enablement`.
  The hosted preview uses a clean SQLite template copied into serverless `/tmp`; this makes
  the governed workflow usable for evaluation but does not provide durable production data.

promoted, the correct handoff timeline, and permission boundaries held over MCP.

## Build Sequence (MVP first)

1. L0 with 3-4 frameworks, persistent context, and one read-only connector category — prove
   deliverable quality and connected usefulness together
2. L1 with explicit write/action access and manual workflow chaining
3. Privacy Scrubber standard mode, on separate encrypted infrastructure from day one
4. L2 automation only (scheduled/triggered workflows, no agent-built tools yet)
5. L2 builder mode (coding agent scaffolding small tools) — engineering loops in here
6. Promote Path — once there's a real backlog of durable L2 builds worth promoting

Full detail: [FRAMEWORK_L0_L1_L2.md](./FRAMEWORK_L0_L1_L2.md#build-sequence-mvp-first)

## Open Design Questions

(carried over from the design-session handoff — not yet resolved)

- Does context bundle content (org glossary, voice, approved sources) get authored by an
  admin up front, or inferred from L0 usage over time?
- Where does "read-only default, write is opt-in" technically live — per connector, per
  framework, or per user role?
- Do the L0/L1/L2 tiers need names people say out loud, or does the tier stay invisible with
  only the capability menu visibly changing?
- Can L2 users introduce entirely new data sources without going through the L1 connector
  walkthrough first, or must Extension bundle builds only use existing bundles?
- Internal/user-facing naming for the vault (Ephemeral Identity Vault / Privacy Scrubber)
  needs testing with actual HR/insurance buyers before being locked in.
- Which framework to build first (Comms 101 vs. Research Assistant) — not yet chosen.

Resolved: stewardship split (technical health = engineering, practice health = domain/product
owner, collapsible to one person for "tiny SaaS"-scale builds). See
[FRAMEWORK_L0_L1_L2.md](./FRAMEWORK_L0_L1_L2.md#open-questions-to-resolve-next).
